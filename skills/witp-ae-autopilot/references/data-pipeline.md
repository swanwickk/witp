# WitP-AE 读层数据管道（存档 / 快照 / 字段）

参谋部看到的一切都来自这条管道。参谋「给错数据」绝大多数是管道问题，不是参谋本身故障——先按本文核对，再决定是否修复参谋。

## 一、存档槽位语义（最易错）

引擎结算后**依次**写两份存档，语义相反：

| 文件 | 含义 | 用途 |
|---|---|---|
| `wpae000.pws` | Autosave —— 结算后**新状态** | 当前局面，常规研判读这份 |
| `wpae002.pws` | PreTurnSave —— 结算前**旧状态** | 与 000 对比「上一步 vs 现在」 |
| `wpae003.pws` | 手动存档槽 | 用户手动存盘 |

**核心陷阱**：读层若硬编码优先读 `wpae002`，整个系统会**永远落后一回合**——参谋给出的回合数与日期和前线所见对不上，前线就会误判「参谋数据源是错的」而弃用它。

- 选档规则：**按 mtime 取最新**，不要按固定文件名优先。
- 自检：`staff --check` 会打印「快照剧本/日期」与「实际存档日期」并给出**快照滞后**秒数；滞后为负且绝对值很大 = 快照落后于存档。

## 二、读层与快照

- 读层脚本 `witp-reader/witp_read.sh [存档路径]`：不带参数时自行选档；**支持显式传入存档路径**，这是「指定存档」能力的底层。
- 快照落盘 `witp-reader/state/turn.json`，键名为 `game_date` / `game_turn` / `scenario_name` / `header_comment`。
- 看板是**拉取式**：游戏推进不会自动重跑读层。靠 `witp-watcher.service` 轮询存档 mtime，变动即重跑。
- 读层开头 `rm -rf state/` 再重建存在**空窗期**（此间读到「未知剧本/第1回合」）。防护：执行前 rsync 备份到 `state_lastgood/`，失败自动回滚；后端读 `turn.json` 时**先 `state/` 后 `state_lastgood/`** 两级兜底。
- `perception.capture_state(save_path=..., run_scraper=...)` 是读层封装，**本就支持指定存档路径**；新能力通常只需把它暴露到 CLI/API，不必改读层。

## 三、JSON 字段名（取错字段 = 编造标识）

**编队**（`taskforces.json`）**没有 `id` / `name` 字段**：
- 标识用 `record_id` —— **即游戏内 TF 编号**（`record_id=14` → `TF14`，正好对应 `witp-cmd set-dest TF14`）。
- 显示名用 `flagship_name`。
- 位置用 `start_of_day_x/y` 与 `target_x/y`（无 `coords` / `hex`）。

**航空队**（`airgroups.json`）：
- 标识用 `record_id`，名称用 `name`（**可能为空**）。
- 空名条目**不可执行**，生成指令时应跳过，不要退化成 `AG#0` 这类占位编号。

**教训**：取不到字段时回退到 `"TF1"` / `"AG#0"` 这类兜底值，等于**编造出前线无法执行的部队编号**，比报错更有害。取不到就跳过，或明确输出「未知编队」。

## 四、故障对照表

| 症状 | 诊断 | 处置 |
|---|---|---|
| 参谋日期/回合与前线所见差一回合 | 读层读了 `wpae002` 而非最新存档 | 改为按 mtime 取最新；或显式 `staff --save 000` |
| 看板长期显示旧剧本/旧日期 | 拉取式管道没人触发 | 查 `witp-watcher.service`；`POST /refresh-state` 手动刷新 |
| 看板闪「未知剧本/第1回合」 | 读层 `rm -rf state/` 空窗期 | 检查 `state_lastgood/` 兜底是否生效 |
| 刷新报「已有刷新任务在执行」且长期如此 | `/tmp/witp_refresh.lock` 残留 | `staff --fix` 清锁；后端应有 **600s 残留锁自愈** |
| 参谋给出不存在的部队编号 | 取错字段 | 改用 `record_id`（见第三节） |
| 看板显示健康但对局实际已停 | 体检判定没比对存档 | 体检须读两份存档取最新日期做对照 |

## 五、锁与并发（通用工程陷阱）

`O_CREAT|O_EXCL` 建锁 + `finally` 删锁的模式，在**请求被中断**（客户端超时、进程被 kill、前台转后台）时 `finally` 可能不执行，锁**永久残留**，此后所有请求全部失败——症状是「按钮突然全都没反应」。

- 必配**年龄自愈**：锁龄超过阈值（本项目 600s）即视为残留，强制接管。
- 锁内写入 PID 便于排查；冲突报错要**给出可操作的恢复命令**（`witp-cmd staff --fix`），不要只说「请稍候」。
- 连续快速调用同一刷新接口会撞锁并返回 409——**测试时单发调用**，别把并发锁误读成功能坏了。
