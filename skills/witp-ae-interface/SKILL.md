## 坐标基线与窗口层级（2026-09-24 实测，一次漂移事故后固化）

### ★ 唯一事实源：屏幕 = 1400x1050，游戏窗口 = 1024x768，偏移 = (188,150) ★

**四处基线必须同步，改环境即同提交改全**（曾因只改一处造成长期矛盾 + 守卫假警报）：
| 位置 | 当前值 |
|---|---|

| `witp-ae-autoplay/SKILL.md` | 1400x1050 |

### 窗口层级（决定「归位该动谁」）
```
root
 └─ openbox frame (+1,+20)            ← openbox 管理，带装饰
     └─ Wine Desktop (4194311)         Override Redirect = no   ← openbox 管理
         └─ War in the Pacific (16777217)  Override Redirect = yes  ← openbox 不管
```
- 实测 `xwininfo -root -tree`：游戏窗口是 Wine Desktop 的**子窗口**，相对 `(0,0)`，绝对 `+188+150`。
- **游戏窗口绝对位置 = 容器位置 + (0,0)，它自己不会独立漂。**

### ★窗口操作三条铁律★（违反会造成二次漂移）
1. **归位只操作容器**：用 `wmctrl -i -r <WineDesktopID> -e 0,187,130,1024,768`，或直接用固化函数 `witp_recenter`。**严禁 `xdotool windowmove` 游戏窗口**——它是 override-redirect 子窗口，移它只是在父容器内挪位，父容器不动 → 两者错开，越修越漂。
2. **游戏窗口永不直接 windowmove**：`xdotool windowmove` / `windowunmap`+`windowmap` 一律禁止用于 16777217。要动只动 Wine Desktop。
3. **`witp_fix_mouse` 已改为操作 Wine Desktop**（旧版误操作游戏窗口）。

### ★图先验后读★（杜绝拿错位图推理）
- **出界拒拍**：`witp_crop_ok` 校验 `OX≥0 且 OY≥0 且 OX+1024≤屏宽 且 OY+768≤屏高`，出界直接 return 1，不产出可疑图。
- **出图断言**：`witp_shot_game` 出图后校验尺寸必须精确 `1024x768`，否则报错拒读。
- **教训**：漂移到 (-134,165) 时 `convert -crop` 照样出图（黑边/错位），我拿错位图连续误判「存档对话框点不动」是对话框问题——**实际是图本身就不可信**。图不对，一切推理作废。

### 修复动作的正确顺序
```
1. witp_sync_offset            → 读当前偏移
2. witp_crop_ok                → 出界？出界则 3，否则 4
```

## ★set-dest 探针法：四个致命缺陷与修复（2026-09-24 定位，先已修复）★

**症状**：`witp-cmd set-dest` 反复报「探针未读出坐标，采用默认基准」→ 用错误基准反算像素 → 点击错位 → 航向不变或设错格，且回读为 None。

**四个叠加缺陷均在 `_read_tf_dest_from_list()`（读 T 列表 Location 列）**：
| # | 缺陷 | 修复 |
|---|---|---|
| 1 | 裁剪 `700x260+150+220`（x 仅到 850），**Location 列实际延伸到 ~1010** → 读不到 | 扩到全宽（x=140..1024） |
| 2 | 正则要求**半角逗号** `\s*,\s*`，但 tesseract 实测读成**点号或空格**（`moveto 106.142` / `moveto 106 142`）→ 恒不匹配 | 改用非数字分隔 `\D{1,3}` |
| 3 | 用**整块 psm6** OCR，把 TF 编号读错（`14`→`_ 14`、`15`→`45`） | 改为**按行带逐行裁剪 + 单行 psm7** |
| 4 | 行左侧**地图标签文字混入**（`tagula`、岛名）干扰行首编号 | 裁剪起点右移到 **x=140** |

**定位策略**：① 行首编号匹配（主）；② **行序兜底**（T 列表数据行按编号升序，当前 11 个 Human 编队顺序固定为 `14,15,16,17,18,20,21,22,23,24,25`，行 y = `250,264,278,292,306,320,334,348,362,376,390,404`，行距14）。

**已知残留局限**：tesseract 对数字 `0/5/6/8` 仍会误读（实测 `106`→`108`）；目标为**地名**（如 “Deboyne Islands”）的行本就无坐标。**最终以读层 `target_x/y` 为准**。

**修复后实测**（同一次调用即可全程跑通）：
```
探针成功标定: (500, 500) 对应 Hex(112, 144)
真实目标 Hex(105, 145) → 点击像素 (200, 538)
✓ 编队 14 航向设为 (105,145) 经回读确认生效
```

**加固②探针合理性校验 + 缓存**（防止 OCR 字型误读污染标定）：
- 探针点 `(500,500)` 对应的 hex **由屏幕位置决定、与操作哪个编队无关**（实测 TF16/18/20 均读出 `(112,144)`）。
- 但个别编队因字型固定误读会得到**稳定但错误**的值（TF15 恒读成 `(412,144)`）→ 错误基准反算 → 把 105,146 设成了 98,146/118,146。
- 对策：① 合理性校验（珊瑚海地图有效范围约 `x=86..132, y=110..170`，超出即判误读）；② 最多重试 3 次；③ 仍失败则**复用 `/tmp/witp_probe_cache.json` 已成功标定值**。
- ★坑★ 该缓存函数依赖 `json` 模块，而 `witp-cmd` 原**未 import json** → `NameError` 被 except 吞掉 → 缓存恒返回 None。加 `import json` 后才生效。

### ★加固③：探针值会漂移，且单次 OCR 会把 101 读成 111（2026-09-24 实测）★

- **探针 hex 不是常量**：实测从 `(112,144)` 漂到 `(101,155)`（地图视图滚动所致）。**任何硬编码的探针基准都会过期**，必须每次现标，且标定值要随视图变化而更新。
- **单次读数不可信**：OCR 会把 `101` 读成 `111`（首位数字重复），而**两个值都落在合理范围 86..132 内**，单次范围校验完全拦不住 → 实测 TF14 因此被设成 `(92,143)`，与目标 `(102,143)` 差了 10 格。
- **对策（已落地）**：
  1. **多次采样取众数**：连续标定 2~3 次，取出现次数最多的值；连续两次一致即提前收手（省时）。
  2. **全不一致 → 回退缓存** `/tmp/witp_probe_cache.json`。
  3. **`--probe x,y` 手动指定**：已知探针时跳过 OCR，例 `witp-cmd set-dest 14 102 143 --probe 101,155`。
- **★预滚动已重建（2026-09-26）★**：VNC 方向键**确实能平移地图**，每按一次 **2 格**（right/left 改 X、down/up 改 Y），且**完全可逆**（实测 down×4 后 up×4 精确回到原值）。旧"方向键不滚动地图"的结论是**错的**（那次用了 xdotool）。现 `_ensure_visible` 改为：按"需平移格数 ÷ 2"连按，滚动后**解析式更新基准**（b += ±2×次数），不再慢速重探针。⚠️ 残留 bug：滚动量与 `_to_px` 的比例尚未对齐，长距离滚动后基准仍会漂 → 表现为多轮 ❌（**好处是它如实报错、没有假成功**）。

### ★加固④：单点探针的根治方案——闭环纠偏（2026-09-24 实测）★

**问题**：单点探针标定对「两次点击之间地图视图发生滚动」毫无抵抗力。实测同一探针点连续读出
`(114,155) → (108,155) → (107,160) → (106,155)`，每次都不同 → 点击落到错格。
（根因：WitP 在选中/点击时可能重定位地图视图，故任何单次标定值都会过期。）

**根治做法（已实现于 `cmd_set_dest` F 段）**：放弃「一次标定 → 一次点击」，改为**闭环迭代**：
```
1. 用当前基准算点击像素 → 点
2. 回读实际落点 landed
3. 若 |landed − target| ≤ 1 → 成功，把当前基准写回缓存
4. 否则 基准 += (landed − target)，重试（最多 3 轮）
```
- 该法**不依赖探针精度**，只依赖回读可用；实测 TF16 一轮就把 2 格残差收敛。
- 残差通常 ≤2 格；靠近屏幕上下边缘时 `clamp(30,740)` 会造成固定偏差。
  （旧文写"纵向 37.5 px/格"——**该值已作废**，权威值是 **37.0 px/格**，见《地图标定权威值》。）

**仍存在的硬限制**：`_read_tf_dest_from_list` 对个别编队（如 TF14）**恒返回 None**（坐标含 OCR 易混字符）。
此时闭环无从纠偏 → **必须承认这是工具能力边界**，改以「结算后 Autosave 的 `target_x/y`」为权威核验，
不要在当回合反复重试（重试只会重复点击、浪费时间且可能落到别的格）。

### ★核验的正确姿势：回读不可全信★
- **回读为 None 不等于失败**：先比对打印出的「点击像素」是否与已成功案例一致。实测 TF14 点击 `(543,50)` 与 TF16 成功时**完全相同** → 实际已设对，只是回读 OCR 失败。
- **权威核验 = 读层存档 `target_x/y`**（须过回合后才有新值）。
- **过回合前的即时核验**：截图 → 裁剪 T 列表区域 → 用 **`vision_analyze` 读 Location 列**。tesseract 对 `0/5/6/8` 误读率高，vision 明显更可靠（实测 vision 正确读出 `move to 102,143`，以及舰船数 6/9，与读层一致）。

## 中文字体：游戏 GUI 只认 Wine 内置 System 位图字体（实测）

- 症状：航空队/编队列表里中文名整片空白，只剩名字里的 ASCII 部分（“澳大利亚空军第23中队”→只显示 `23`；机型“挑战”→完全空白）。
- 根因（`WINEDEBUG=+font` 日志，53,972 条请求）：游戏 GUI 走 `CreateFontA("System", h=16, weight=700, charset=134)`，Wine 把它匹配到内置位图字体 `/usr/share/wine/fonts/svgasys.fon`（只有拉丁字形）。注册表 `HKCU\Software\Wine\Fonts\Replacements` 里的 `System=SimSun` 被 Wine 静默忽略（日志中 `add_family_replacement ... to L"System"` 计数为 0）；把改名字体的 TTF 放进前缀 `C:\windows\Fonts` 也不够——同族里内置位图面仍胜出（`Chosen: L"System Regular" (svgasys.fon)`）。
- **修法（进程级、不动系统文件）**：① 用 fontTools 把文泉驿正黑（`/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc` 第 0 个字体）name 表改成 family/fullname=`System`、subfamily=`Regular`，另存到前缀 `C:\windows\Fonts\system-cjk.ttf`（OS/2 代码页已含 CP936 位 0x40000）；② `witp-launch.sh` 里 `unshare -m --propagation private` 后 `mount --bind <只排除 svgasys.fon 的软链目录> /usr/share/wine/fonts`。实测日志变为 `Chosen: L"System" (C:\windows\fonts\system-cjk.ttf)`，菜单/选项/状态栏等 GDI 文字中文正常。用 `ls /proc/<游戏PID>/root/usr/share/wine/fonts` 可验证命名空间生效。
- **但列表/详情页的中文仍显示不出来——这是英文原版 exe 的固有限制**：字体日志里游戏向 GDI 只发过 512 次单字符 `NtGdiExtTextOutW`，字符一路到 `\007f` 为止，**一次中文都没请求**（600k+ 行日志里高于 0x2000 的转义计数为 0）。即游戏自己按 ASCII 建字形表绘制对话文本，与 Wine 字体无关；菜单里看到的中文是汉化版替换的位图美术（ART/*.bmp）。
- 结论：想让游戏内名称可见，只能走“数据改英文”路线（见下），或接受中文名在对话界面为空、由读层从存档取中文名（报告仍是中文）。

## ★★实例活性体检：禁止在「尸体/僵尸」上做任何测量（2026-10-09 定案）★★

**这是本工程重复犯过 3 次、代价最大的错误。**

**症状**：输入（键盘或鼠标）"毫无反应"，画面 md5 恒定不变。
看起来像"输入通道失效"。**真实原因往往是整个模拟已停摆，或实例已死**。

**已实测的两种"假死"形态**：
| 形态 | 主进程 | X 窗口 | 输入 | 判据 |
|---|---|---|---|---|
| **残影窗口** | **已退出**（`/proc` 无该 exe） | 仍在、`IsViewable` | 无反应 | `ps`（用 `/proc/*/cmdline`，**不要用 `ps comm`**，它截断成 15 字符） |
| **管道阻塞** | 活着但主线程 `wchan=anon_pipe_read`、CPU 0% | 仍在 | 无反应 | `cat /proc/<pid>/wchan` |

> ⚠️ `ps -eo comm` 只显示 15 字符 ⇒ `War in the Pacific Admiral Edition.exe`
> 被截成 `War in the Paci`，`grep -i witp` **搜不到** ⇒ 会误判"进程已死"。
> 必须读 `/proc/<pid>/cmdline`。

**★唯一可靠的活性判据 = 输入-响应探针★**（`workspace/witp_preflight.py`）：
```python
from witp_preflight import assert_alive   # 不健康直接抛异常
assert_alive()
```
内部逻辑：VNC 发 `Escape×2` → 记截图 md5 → 发 `t`（必开编队列表，画面必变）
→ 再记 md5 → 比对 → 发 `Escape` 复原。变化=活；不变=死/挂起。

**★三个反面判据（都曾误导我，勿用）★**：
1. **"两帧相同" ≠ 死亡**：地图静置时游戏**根本不重绘**（只在有变化时刷帧），
   两帧相同是正常的 ⇒ 该判据会把健康实例误判为死。
   只有「**发了输入**仍不变」才是死亡证据。
2. **`witprec.exe` 不在 ≠ 死亡**：实测 witprec 已经退出时，Esc/T/F 全部正常生效
   ⇒ witprec **不是运行期常驻进程**，它可能只在解码/播放时被拉起，用完即退。
   我曾据此断定"僵尸"，**已实测推翻**。
3. **`xdotool` 发键无反应 ≠ 输入通道失效**：游戏不认 XTEST 注入，
   用 xdotool 测探针会在**健康实例**上误报"输入无响应"（假阴性）。
   探针必须走 **VNC（5902）**：`python3 witp_vnckey.py t`。

**结论**：凡出现"输入无反应"，**先跑 `witp_preflight.assert_alive()`**，
不要直接下"机制无效"的结论 —— 否则会把尸体现象写成配方，害很多轮。

## ★★set-dest 的真实模型（2026-10-10 地面真值标定，已实机验证命中）★★

**模型**：进入选格模式（点 `Set TF Destination` 箭头 → 面板关闭）后，
点击像素 (x,y) 设定的目的地 = `视野中心 C + ((x−512)/37.0, (y−384)/37.0)`。
**C = 视野中心格**，由「点屏幕正中 (512,384) → 面板回读 `Hex:`」**直接测得**（屏幕正中恒为视野中心）。
比例 W=H=**37.0 px/格**（实测：横 ±200px→±5.4 格、纵 ±100px→±2.7 格，全部命中）。

**★旧实现失败根因★**：用「小地图黄框」推算视野中心。黄框映射有约 **(+3.24,+3.06) 格**
的系统偏差，据此算出的落点像素整体偏约 **9 格** ⇒ 工具**报成功但实际设错格**
（这是 set-dest「不收敛/假成功」困扰多版的真身）。

**正确配方（已验证）**：

## ★★读层核验的时序铁律（2026-10-10 实证）★★

读层 JSON 的 mtime 必须与存档 mtime 一致才可信。

## ★★启动流程（`witp-cmd launch`）：三条致命坑（2026-10-09 实机验证 ok=True）★★

**① 绝不在主菜单按 Escape ★决定性对照实验★**
游戏启动约 **45 秒**时已到**主菜单**（实测亮度 71，约 45s 后菜单才成形）。
此时 `vnc_key("escape")` 会被游戏当作**退出**处理：
服务立刻 deactivating、窗口消失、日志尾 `FreeHeap`。
⇒ 这正是「launch 起来几十秒就死」的**真凶**（此前长期误判为 cgroup / 时序）。
**对策**：启动后**不按任何键**，只轮询等主菜单文字出现，然后直接点按钮。
（开场简报只在**进入地图后**才需要用 Esc 清。）

**② 必须经独立 systemd 服务启动，且禁用 `pkill -f`**
- 旧实现 `subprocess.Popen([launch.sh])` 从 agent shell 起 ⇒ 游戏寄生
  `hermes-web-ui` cgroup ⇒ 该服务重启即连带被杀（见下节）。
- 旧实现 `pkill -9 -f "<exe名>"` 的 `-f` 匹配**完整命令行**，会命中执行它的 shell 自身 ⇒ 自杀。
  **正确**：读 `/proc/<pid>/exe` 的可执行文件名匹配后再 kill。

**③ systemd `TimeoutStopSec` 默认 90s，而 wine 忽略 SIGTERM**
⇒ 每次 `systemctl stop` **干等 90 秒**，`stop→start` 时序极易踩空
（新旧实例争抢 X 窗口/前缀 ⇒ 新实例 `InitHeap→FreeHeap` 启动即退）。
**对策**：unit 里加 `TimeoutStopSec=5` + `SendSIGKILL=yes`（实测 stop 从 90s 降到 6s）。
且 `systemctl stop` 是**异步**的 ⇒ 必须「最短等 8s + **连续两次**读到 wine 残留=0」才认定清干净
（早先版本第一次判断就读到竞态性的 0，于是立刻 start 而踩空）。

**★可泛化的元教训：凡「UI 屏检/回读」都不可作硬闸★**
实证两例：① `set-dest` 的面板回读返回的是**该 TF 当前目的地**（多次读数漂移），
旧版拿它判命中 ⇒ **机制上不可能成功**；
② `launch` 的 OCR 屏检**逐帧波动**（同一屏我单独测能命中、launch 内却超时，
而那次点击**实际生效**）⇒ 把已走通的流程判死。
**正确姿势**：过程判据只作日志；硬判据用**结算后读层**（set-dest）或
**服务/窗口状态**（launch：`svc==active && 窗口存在`）。

## ★★启动隔离：游戏必须在独立 systemd 服务里跑（2026-10-09 定案，最省事的崩溃根治）★★

**症状**：游戏「跑 1.5~3.5 小时必崩」，或输入突然全无反应、画面冻结。
**真身**：从 Hermes 终端（agent shell）启动的游戏**寄生在 `hermes-web-ui.service`
的 cgroup 里**。该 unit 是 `Restart=always` + `KillMode=mixed`；
`apt-daily-upgrade` 等重启它时，systemd 会 **SIGKILL 整个 cgroup**，游戏被连带杀死。

**现场证据**：
```
journalctl: hermes-web-ui.service: Killing process 3076996 (plugplay.exe) with signal SIGKILL
            同时 Stopping witp-openbox98 / witp-xvnc98d
游戏侧日志: XIO: fatal IO error 25 (Inappropriate ioctl for device) on X server ":98"
            （随后主游戏进程从 /proc 消失）
```
**修法**：用独立服务启动（本仓已建 `/etc/systemd/system/witp-game-en.service`）：
```bash
systemctl start witp-game-en     # ExecStart=witp-launch-en1108.sh，独立 cgroup
```
验证：`cat /proc/<game_pid>/cgroup` 应显示 `/system.slice/witp-game-en.service`。
**隔离后实测连续跑完 9 个回合无崩溃**（此前每局必崩）。

> ⚠️ 窗口/进程检查**都要看 cgroup**：同一时刻可能既有 systemd 实例、
> 又有寄生在 web-ui cgroup 的游离实例（后者会在 web-ui 重启时死掉）。
> 清理游离实例时**按 `/proc/<pid>/exe` 的可执行文件名匹配**，
> 切勿用 `tr </proc/<pid>/cmdline | grep` 匹配 —— 匹配串会命中**自己这条命令**从而自杀。

## ★★小地图 = 视野控制主通道（2026-10-06 用户澄清 + 实测定案）★★

> ⚠️ **本节为历史记录（2026-10-06）**。更权威、更新的版本见本页上方
> 《视野导航：小地图黄框法（2026-10-09 实测定案）》与《视野机制定案表》
> —— 那两节已修正本节的「一步到位/唯一可靠」表述（实为**粗调**，
> 精度上限 纵 1.44 格/px、横 0.52 格/px）。**框坐标与映射仍以本节为准。**

**用户澄清的语义（权威）**：
- 小地图 = **整个太平洋区域图**
- **红框 = 当前剧本的限制区域**（珊瑚海剧本只有这块可玩）
- **黄框 = 屏幕当前视野**

**实测框坐标**（游戏窗口内，`mmframe.py` 颜色掩膜）：

| 框 | x 范围 | y 范围 | 尺寸 |
|---|---|---|---|
| 白框（小地图外框） | 894–1018 | 662–767 | 124×105 |
| **红框（剧本限制区/可点区）** | **939–964** | **715–744** | **25×29** |
| **黄框（当前视野）** | 948–959 | 724–732 | 11×9 |

### ★只在红框内点击才生效★
实测点红框外 `(1010,760)`、`(860,675)` → 视野**纹丝不动**（被游戏忽略）；
点红框内 `(939,743)` → 视野**一步跳到目标旁**。这是长期误判"小地图无效"的真正原因。

### 小地图 → Hex 映射（三点实测定案）
```
mm(941,717) ↔ hex(100,116)
mm(962,742) ↔ hex(111,152)
mm(941,742) ↔ hex(100,152)
⇒ 横向 1 格 = 1.909 mm-px
⇒ 纵向 1 格 = 0.694 mm-px（精度差，1px≈1.4 格，必须闭环微调）
```

### 效果：**粗调**（不是精定位）
点 `(939,743)` → 视野中心 `(100,152)`，目标 `(99,153)` 偏差 (-1,+1) —— 这是**最好情况**。

> 136.9 一步推到 149.1）。⇒ **小地图只能把目标"拉进主屏"，精定位必须回主地图**。
> 另：目标落在红框边缘时会被 `clamp` 到边线，此时点击可能被**边缘死区**吞掉
> （实测 target(99,153) → mm(940,743) 贴 y=744 边缘，多次点击视野不动）。

## ★★视野机制定案表（2026-10-09 用「黄框判据」重测，以本节为准）★★

> ⚠️ 本节**取代**下面历史小节里的同类条目。判据统一为**小地图黄框**
> （视野的真实指标，见《视野导航：小地图黄框法》），不再用"主地图指纹"

> 而锚点回读一动没动）。

| 机制 | 实测结论（黄框判据） |

| 点**主地图**像素移视野 | **不移** —— 连点 5 个相距很远的像素，黄框纹丝不动 |
| **边缘悬停**滚动 | **本实例在"离边 20~45px 处"测四向不动** —— 但已知**触发带仅约 1px**（见 doctrine §视野导航），故 **该测试不足以否定**，属**未定论**。要复测必须把鼠标停在**窗口绝对最外 1 像素**。⛔ 勿据内缩位置的一次否定写"边缘滚动无效"。 |
| **小地图点击**跳视野 | **★有效★** —— 红框内点击必改变视野（绝对定位，不累积误差） |
| 历史 `witp_nav.goto()` | **机制假设错误** —— "点像素 P ⇒ 视野居中到 P"已被实测推翻 |
| **拖拽**滚动 | **未定论** —— 禁引用任何一方 |
| 顶栏 `Hex:` 作视野判据 | **不是视野** —— 它是**选中对象所在格**（面板开着时恒读该对象自身位置） |

## ★witprec.exe 空指针补丁（启动崩溃根治）★

**崩溃现场**（winedbg 实测）：`EIP:00438a86  ESI:00000000`，
指令 `movl 0x44(%esi),%esi` 解引用空指针。

**成因**：`0x438a81` 的 `call 0x599370` **不保存 esi**（无 push/pop esi），
返回后 esi 已被破坏；紧随的判空 `test %esi,%esi` 在解引用**之后**，来不及。
**对照证据**：同文件 `0x4389F0` 处的同款函数顺序正确（先取链表头、先判空）。

**修法**（`workspace/witprec_patch.py`，7 字节原地重排，无相对跳转需修正）：
```
原: 8b 76 44  85 f6  74 3a     mov 0x44(%esi),%esi ; test ; je +0x3a
新: 85 f6     74 3d  8b 76 44  test ; je +0x3d ; mov 0x44(%esi),%esi
```
备份 `witprec.exe.orig2`，`--revert` 可回滚。

## ★quartz.dll 越界断言补丁（运行期崩溃，★32 位★）★

**关键：崩溃进程 `0120` 是 32 位**（主游戏 `0138`、witprec `0140`），
加载 `/usr/lib/i386-linux-gnu/wine/i386-windows/quartz.dll`。
补 64 位版本**完全无效**（改了断言照旧）。

**★系统有两份 32 位 quartz，必须都补★**：
```
/usr/lib/i386-linux-gnu/wine/i386-windows/quartz.dll     (libwine:i386)
/usr/lib/x86_64-linux-gnu/wine/i386-windows/quartz.dll   (libwine:amd64)
```

**正确落点**（`0x1000a2fc` 是错的！见下）：
| 版本 | 越界跳转 | 正确落点 |
|---|---|---|
| i386 版 | `0x1000a2d0` (jb), `0x1000a2e1` (jae) | **`0x1000a303`** |
| x86_64 版 | `0x1000a248` (jb), `0x1000a259` (jae) | **`0x1000a27e`** |

> ⚠️ **教训**：最初把落点设成 `0x1000a2fc`，那是「正常路径入口」，
> 首句 `movl $0x0,-0x8(%edx)` **解引用野指针 edx** → 把断言崩溃换成
> `page fault on write access to FFFFFFF8`。
> 正确落点 `0x1000a303` 跳过该写，而 `edi` 本次迭代已赋值为 `&filter->sample_cs`，
> 可安全用作 `LeaveCriticalSection` 参数。

**上游 Wine 至今未修**：实测 wine-mirror/wine master 的 `dlls/quartz/filesource.c`
第 397 行仍是原封不动的 `assert(req >= filter->requests && ...)`。

**工具**：`workspace/quartz32_patch.py --check|--apply|--revert`（双路径版）。

**实测稳定性**：witprec 补丁 + 两份 quartz 补丁 → 游戏稳定运行 **1h27m+**。

> ⚠️ **★★2026-10-09 重要更正：quartz 补丁不是「跑一会儿必崩」的根因★★**
> 我在 `witp-launch-en1108.sh` 里把 quartz 补丁**停用**后实测：
> 游戏**依然**在运行 ~3.5 小时后卡死 —— 但那次卡死的真凶是 **cgroup 连带被杀**
> （见本页《启动隔离》节），而不是 quartz 断言。
> 现场复现：`witprec.exe` 退出 + 主进程卡在 `anon_pipe_read` + 日志有
> `err:ole:com_get_class_object ... {62be5d10-...}`（DirectShow 类创建失败的**常规噪声**，
> 在成功运行的局里也一直出现，**不是崩溃信号**）。
> ⇒ **结论订正**：
>   · 崩溃有**两个独立来源**：① quartz 断言（已补丁）；② cgroup 连带被杀（已隔离）。
>   · **先做 cgroup 隔离**（一行 `systemctl start witp-game-en`），这是最省事、收益最大的一步；
>     quartz 补丁是额外保险，且**停用后游戏仍能跑**（本轮就是停用状态下跑完 9 回合）。
>   · `com_get_class_object` 噪声**不可**用来判定崩溃。

### 3. 目的地读取器的三个缺陷（都会让 set-dest 失去反馈）

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **多行串读** | 读出 `Lunsa. moveto moveto 108.135 moveto 108.135` | 行距仅 14px，而“行心±6”裁剪窗高 13px 会串行；**改用行带自身上下界**裁剪 |

| **字形歧义** | `moveto LO? 141`（1↔L、0↔O、9↔S） | 通用 OCR 拿不到坐标时，用**数字白名单再读一次**兜底；**数值段绝不做字母→数字归一** |

### 4. set-dest 的 px/格 比例是**本地量**，必须在线自标定

同一局内实测到过 **4.44 / 10.00 / 15.00 / 24 / 30 / 37.5 / 40 / 48** px/格 ——
**随视野变化**，写死任何常数都会过冲或爬行。

- **在线自标定**：第 1 轮点画面中心取基点 `(P0↔H0)`；第 2 轮点 `P0+对角120px` 得 `(P1↔H1)`
  ⇒ `W=(P1x-P0x)/(H1x-H0x)`，H 同理；第 3 轮起按实测比例瞄准。
- **滚动再标定**：每轮拿新的 `(像素↔格)` 点与上一点重算比例，越跑越准。
- **★合理性闸门（必须有）★**：只接受 **5~60 px/格**；超范围一律沿用上次好值。
  实测一次 OCR 误读就把比例推成 `0.16 / -2.00`，之后校正量≈0，**循环原地踏步 8 轮**。
- **最小步长 1.4 格**：误差非零时给 `max(|err|*scale, 1.4*scale)`，否则约一半轮次跨不过格边界（实测第 4/6/7/8 轮落点完全不变）。
- **轮次上限给足**（实测 10 轮常不够，14 轮较稳）：每轮约 25 秒，慢但能收敛。

### 5. `--no-jump`：set-dest 自带的小地图跳转会破坏调用方刚摆好的视野

实测：手动把视野移到 (100,144) 后，`set-dest` 自带的跳转又把它挪回 (113,152)，

### 6. 小地图是**视野控制手段**（绝对定位），映射非线性

- 点小地图**红框之外** → 视野真的跳过去（点红框内三点得到逐字节相同的画面，即只是重新居中）。
- 实测映射（本剧本 view 中心 → 所需 minimap 像素）：`(900,722)→(100,119)`、`(895,730)→(100,135)`、
  `(902,735)→(100,144)`；**x 方向反向、且会饱和**（再多点也不再变）。
- 可靠用法：**点小地图 → 用“探针”读视野中心 → 迭代逼近**，不要指望一次算准。

### 7. 长距离精确落子的**最可靠办法 = 手动闭环**

