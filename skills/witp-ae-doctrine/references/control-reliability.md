# 控制层：标定配方、并发修法、能力边界

配套 SKILL.md §3.9（静默空输出）与 §5.8（核验口径）阅读。
**本文件只放那两节没有的配方与架构**，不重述核验铁律本身。

## 1. 地图几何标定配方（根治系统性偏格）

> **★本节的取样方法已作废，勿照做★**：原配方以**顶栏 `Hex:`** 作为取样读数源，
> 而顶栏已定案为「**光标 / 高亮框所在格**」（连写形态需拆位，且拆出的坐标必须落在基地包围盒内才可信，
> 见 `perception-channels.md` §一）。
> 其可用性有限：**它只在「点击/移动确实改变了高亮框」时才更新**，故不能无条件当探针；
> 且**「点击地图 ⇒ 视图滚动」本身不成立**（直接点地图只挪高亮框 ~0.4%），
> 所以「用点击去滚到目标格再读中心」这条路是断的。
> ⇒ **「实测横向 42.86 px/格、常量本来没错」这条反证一并作废。**
> 当前可用的定位/落子路径见 `perception-channels.md` §一（列表导航 + 现场两点标定 + 落点自证）。
> 下面保留步骤仅作「将来找到更可信读数源时」的参考。

**动比例之前先排除两个更可能的嫌疑**（顺序错了就是在白改代码）：
- ① **探针基准读错行**：基准若取自**实体列表的某一列**，行归并错位时会读到**别的实体**的值，
  整块基准平移，表现为「永远偏同样的格数」。⇒ 基准不得取自跨实体的列。
  （原配方推荐的「顶栏光标格」**该指示器无效**，见上。）
- ② **点击被钳位**（目标超出当前视野，见 §6.3）。

步骤（**读数源待定，勿直接照用**）：
1. 在游戏地图上点若干取样像素，每次点完读**某个已被验证会随落点变化的读数**得到 `(px, py, hx, hy)`。
   **读数源本身就是第一个要验证的东西**；验证方法 = 「让落点改变，读数必须跟着变」。
2. **宽基线取样**：横向跨满视野（≈20 格）+ 纵向取一整列 4 点。**不要**把点挤在屏幕中部。
3. **最小二乘拟合**：x 轴 `px = ox + hx·W`（两参数）；y 轴 `py = oy + hy·H + 奇偶·A`（三参数）——
   把**奇偶半格偏移 A 当自由参数交给数据解**，不要预判它等于 0 还是 H/2。
   解小型正规方程即可，无需 numpy。
4. **MAD 迭代剔除**：算残差 → 用中位数绝对偏差定阈 → 剔掉误读样本 → 重拟合，迭代 2~3 轮。
5. 缓存标定结果，并让动作层**优先用它替代写死的比例**。

**为什么必须宽基线**：采样跨度决定单点误读的杠杆——斜率上的一点点误差会**随距采样区中心的距离
线性放大**，故采样区间越窄，同样一处 OCR 误读撬动的远端偏差越大。
**推论：决不要用一小段屏幕上的样本去推算整张地图的比例。**
（原配方给的具体像素数来自已作废旧读数，已略去。）

**精度口径（别指望标定给格级精度）**：标定的目标只是「落在正确格附近」。
残余的格级误差由**动作闭环**兜底（点 → 回读真实格 → 按差值修正 → 重试）。
⇒ **标定是优化，闭环是保证**，两者不可互相替代。也正因如此，标定不必追求完美，
但必须断言「闭环能在初值 1~2 格内收敛」。

## 2. 读层并发：三件套修法

§3.9 讲了机制（多调用方同写 `state/*.json`，文件尾挂半段 JSON → 解析抛 `Extra data` → 上层静默失明）。
根治修法三件套：

1. **文件锁串行化** —— 读层脚本整体加锁，多调用方排队。
2. **新鲜度复用** —— 结果未过保质期就直接复用，不重读（多数调用其实不需要新数据）。
3. **原子目录切换** —— 在临时目录生成完整结果，最后整体 `rename` 替换，读方永远看不到半成品。

**泛化规则**：任何「多调用方共享一个生成目录」的读层或缓存，都**不允许**用「先删后建」（`rm -rf` + 重建）。

## 3. 判定工具能力边界：看命令面，不看命令数

要回答「这个工具能不能操作整个游戏，而不只是当前剧本」：

- 数**真正能改游戏状态的命令**有几个，列出它们覆盖的域。
  若控制类命令只覆盖「编队目的地 / CAP 百分比 / 搜索百分比」三项，那它就是**单一剧本形状的工具集**——
  换个剧本仍要重写，与命令总数无关。
- 做一张**能力对照表**：游戏需要什么（编队任务·装载·母港·巡逻区 / 航空队任务·目标·转场 /
  基地建设 / 地面部队 / 舰船修理 / 政治点 / 工业）对照「已有 / 缺口」，逐域标出。
  缺口里最有信息量的是**结构性缺口**，而不是缺命令：
  - 坐标写死（面板一动就失效）
  - 核验只有「回读确认」（见 §5.8：它会撒谎）
  - 比例写死（见上节）
  - **按屏幕配方写而不是按实体写** —— 没有「按 id 直达任意基地/编队/航空队」的能力，
    所以每个剧本都要重写一遍界面流程

## 4. 目标架构（自下而上，下层是上层的唯一地基）

```
L4 语义意图层  <动词> <实体> <参数>          ← 与剧本无关的命令面
L3 动作执行层  动作 = 导航 + 控件操作 + 强制核验（每个动作自证）
L2 界面发现层  运行时控件发现 + 地图几何标定
L1 导航层      按 id 直达 任意基地/编队/航空队/地面部队/舰船
L0 真值层      .pws → JSON                   ← 已有，全剧本通用，最扎实
```

四条不可妥协的原则：
1. **真值只认 L0 或界面自身的复读**（顶栏光标格、面板数值）；「点击成功」不算。
2. **坐标不写死**：一律运行时锚定（按行名/标签 OCR 定位 + 邻近重试），或按标定几何换算。
3. **按实体导航**：L0 给出 id，界面必须能跳到任意实体。
4. **验收可证伪**：动作输出 `verified / unverified / failed` 三态 + 证据，不产出二元「成功」。

扩展顺序：**先地基**（标定服务 / 核验框架 / 通用导航），再高价值命令
（航空队：变更任务·高度·转场；编队：变更任务·母港·装载·巡逻区；基地建设），
再地面部队 / 舰船修理 / 政治点，最后工业（战役级剧本）。

## 5. 「工具失灵」先查是不是点错了目标

- 可点的元素常不止一个：**行文字、按钮文字、行首小箭头**都在同一行里。点错一个，
  就会得出「该控件不接受注入输入」的结论——而这是**错结论**。
- 判「通道无效」前，必须**枚举该区域所有可点元素逐个试**，并记录试过哪些、各自结果。
- 同一条通道换个点击目标立刻成功时，结论应记作「目标选错了」，而不是「通道不可用」。
  **错误结论一旦写进技能库，会让后续所有会话都绕开一条本来可用的路径。**

## 6. 感知层静默故障清单（读数「看起来正常、其实是错的」）

配套 SKILL.md §5.8。这些故障的共性：**不报错、退出码 0、日志全是 ✓，真值却是错的**。

### 6.1 截图读到上一帧
- **症状**：某个读数**稳定不变**，怎么点都不动 → 极易误判为「控件失效 / 交互被拒」。
- **机制**：截图封装在断言失败（尺寸不符）时返回非 0 且**不覆盖输出文件**，调用方照样拷贝旧图，
  后续全部 OCR 读的是**上一帧**。
- **处置**：截图前**先删旧图**；截图后校验**存在且 mtime 新鲜**（不新鲜则重试）再拷贝。
  任何「读数卡住」的排查，第一步先确认画面本身是新的。

### 6.2 读数解析接受残缺串
- **症状**：读数偶尔变成另一个**看似合法**的值（如 `Hex:100 140` 被读成 `(40,14)`）。
- **机制**：三重叠加 —— ①裁剪起点太靠右，首位数字被切掉；②二值化阈值毁掉抗锯齿笔画、丢字；
  ③解析器按固定位数切分，把残缺串当合法输入接受。
- **处置**：裁剪**留足左边距**；优先用对比度拉伸而非二值化；解析**必须要求标签在场 +
  最短长度（≥5 位）+ 与上次读数做跳变校验**；校验不过**报错，不猜**。
  静默返回错值比读不出更危险。

### 6.3 目标超出视野 → 不能再「点地图把视野滚过去」
- **症状**：点击「永远落回基准点」，多轮重试毫无变化。
- **机制**：目标换算出的像素超出可点区域 → 被钳到边缘 → 实际点在自己附近。
- **处置**：点击前判断像素是否落在可点区内；不在则**先把视图开到目标附近**。
  **★可取范围有硬边界，且以「操作对象自身所在格」为中心★**：
  目的地拾取的可点范围受**当前视野**限制（视野以该编队自身格为中心），
  实测纵向只能取到 ±8~10 格——目标若在其外，**怎么迭代都只会落在边界那一格**。
  ⇒ 遇此情形**不要跑满轮次再报 `failed`**：应**接受「可达最优」，并同时报出它与胜负点的格距**，
  由该格距判定条件是否仍成立。例：目标 `(98,135)` 实取 `(98,137)`，
  距莫尔兹比港仍是 7 格 ＝ 仍在舰载机正常航程内 ⇒ **条件成立，可继续推演**。
  ⇒ 通用形式：**受边界约束时，交付「可达最优 + 离目标还差多少」，而不是交付「失败」**——
  前者让决策层能判断可行性，后者只会把一次可用的结果丢掉。
  ⇒ **★平移手段有三条：① 列表导航（大位移）② 点地图居中到被点格（短位移）③ 边缘悬停滚动（§6.15，只有位移、不可精确控量）★**
  ② 已由**同一输入通道内重复三次 + 对 4 个不同偏移点击做落格预测、4/4 吻合**定案
  （见 `perception-channels.md` §一「顶栏 `Hex:` = 视野中心格」）。
   实测否证的只有：**方向键 / 滚轮 / 双击 / 右键 / 点小地图**（改用生产入口复测后，
   点小地图仍是逐次相同的 0.00%，已定论；方向键 / 滚轮 / 双击 / 右键未再复测）。
   ⚠ **「停边缘」曾被写在这一否证名单里——已被受控实测推翻，见 §6.15，勿再引用该否定。**
   **拖拽未定论，禁引任一方**（同会话内两次观测互相矛盾），不得作导航手段。
  ⚠ **不要再写「平移只有列表导航一条」**——那会把已验证可用的路径从后续会话里拿掉。
  ⇒ 三者分工：**大位移走列表；落到目标格走「点地图居中 + 落点自证」；
  目标超出可点区时用边缘滚动把视野推出去（§6.15）**。
  ⇒ **★“零变化”不可作为“视野没动”的判据★**：地图重绘后地形相似，真发生了位移也可能只差很小比例，
  而“先挪高亮框、真正跳转要看列表”这类推断曾把“已可用的通路”写成“断的”。
  判“视野有没有动”用**顶栏 Hex 读数是否变为目标格**（它已定案为视野中心格），
  不要用全屏像素差的比例去反推。
  **地图平移机制已定案，不要再拿「不知道该怎么滚」当理由**，也**不要再拿多轮重试掩盖能力缺口**：
  它只会空转到超时，并把「做不了的目标」伪装成「偶发点不准」。
  ~~滚动地图 → 重新探针 → 重算 → 点击~~ —— ★该闭环的驱动机制**仍未落地**★：
  「方向键是否滚动地图」的两个相反结论（「不滚动」/「每次 2 格」）**都是在已作废的顶栏读数上得出的**，
  故 pre-scroll 的驱动量**目前无可信依据**。
  **地图平移机制被可信实测确定之前，禁止用多轮重试掩盖能力缺口**：它只会空转到超时，
  并把「做不了的目标」伪装成「偶发点不准」，直接把排障引偏。
  判「视野有没有动」只能用**同一区域截图的逐字节差**，不能用任何读数（见 §6.4）。
  ⇒ **已定案：平移有三条**——**列表导航**（点基地/单位列表里的实体名，大位移）+ 
  **点地图居中到被点格**（短位移，模型见 `perception-channels.md` §一）+ 
  **边缘悬停滚动**（仅位移、无绝对定位，见 §6.15）。
  「小地图 / 方向键 / 滚轮 / 双击 / 右键」均已否证；**拖拽未定论**，
  不要再拿它们回来补 pre-scroll 闭环。

### 6.4 视野会动（比原以为的严重得多）
- **机制**：① **点地图即把视野居中到被点格**（已定案，见 `perception-channels.md` §一）；
  ⚠ 本行旧文曾写「边缘点击会滚动地图」→ 一度被改判为否证 → **现经受控实测再度确证为真**（§6.15）：
  **鼠标停到窗口的绝对最外 1 像素即滚动**。此前的否证之所以出现，是测点离边 3~9 px、没命中那条 1 px 宽的触发带。
  以 §6.15 为准；② 面板内容变化会位移控件；
  ③ **★在「设定目的地」流程中，视野可能在两次点击之间自行改变★**——实测同一流程内
  像素 (500,500)→落格 (99,155)、像素 (542,300)→落格 (10,113)（Δ 达 42 格），
  而另一处测得 240 px = 6 格。**两者相差近 10 倍、不可能共存**（详见 §6.8）。
  ⚠ 上述数值均以**已作废的顶栏读数**为基准，仅作「不一致」的存证，**不可当比例尺用**。
- **处置**：**绝对像素↔格的换算只在视野不变时有效**——长距离 / 跨视图动作一律走 6.3 的闭环，
  不得复用上一次的换算结果；控件坐标一律按标签运行时定位，禁止硬编码。
- **判据**：「视野是否移动」**读顶栏 `Hex` 是否变为目标格**（它已定案为视野中心格）——
  这是直接判据。全屏字节差**只作辅助**：实测点基地列表里的基地名 ~33%（确实跳了），
  而点地图**确实也跳了**（4/4 预测吻合），只是地形相似使字节差很小（~0.4%）——
  ⇒ **不要把「字节差小」读成「视野没动」**，那是本文件曾犯过的错。

### 6.5 实体匹配放宽过头
- **症状**：给 A 的指令，实际改到 B。
- **机制**：名称 OCR 相似（`5↔S`、`9↔g`、`8↔b`、`4↔A`、`1↔i/l`、`0↔O`）且有多个候选时，
  错误放宽到「数字互替」。
- **处置**：**只容许字形混淆，绝不容许数字↔数字替换**（番号数字才是鉴别信息）；
  匹配策略固定为「严格 → 仅在唯一命中时放宽 → 有歧义就报错不猜」，**宁可失败也不串号**。

### 6.6 读数取错行（列表行定位）
- **症状**：给 A 实体读某字段，读出的是 B 实体的值；或换剧本后整块读数失效。
- **机制**：两个缺陷叠加 —— ①列表**行位置写死**（固定行高数组）；
  ②行识别在标识符匹配失败后走**「行序兜底」**（把一组写死的实体编号按行序一一对应）。
  行高会随内容、字号、面板位移变化，兜底一旦错位，
  就把**另一实体的整行数值当成目标实体的读数**返回，而返回值看起来完全合法、毫无异常。
- **处置**：
  1. 行位置**运行时动态切带**（亮度行带检测、或 TSV token 按 y 归并），**禁止写死行坐标**。
  2. 行识别**必须做实体校验**（行首标识符 = 目标实体），且**只容许字形混淆、不许数字互替**。
  3. 校验不通过 ⇒ **返回失败（`unverified`）**，不许「将就返回」。
- **泛化规则（本清单里最贵的一条）**：
  **「兜底返回一个合法但未验证的值」比「返回失败」危险得多。**
  失败会被上游看见、会重试或上报；将就返回的值则**伪装成数据**一路流到决策层，
  事后只能靠真值反查才能发现，且会被误当成「偶发的读数抖动」。
  ⇒ 凡写下 `or fallback` / `if not matched: use default` / 「按行序推出」，
  先问一句：**「这个兜底会不会返回别的实体的数据？」**
  会 —— 就不许有兜底。**兜底只允许用于「同实体的近似值」，绝不能用于「猜是哪一行 / 哪一个实体」。**

### 6.7 编队列表「目的地列」读取配方（§6.6 的具体落地）

**背景**：编队目的地**不能从顶栏 Hex 回读**（顶栏是**固定字段**，见 SKILL.md §5.8）。
唯一来源是编队列表（T 键）的**目的地列**。

**列位（实机实测）**

| 列 | x 范围 | 说明 |
|---|---|---|
| 行首编队编号 | **166 – 182** | **切勿放宽**——放宽到 163 起会混入单位图标，实测 `13`→`43`、`14`→`44` |
| 目的地 | **712 – 1000** | 行尾 |

行距 **14px**。行带用亮度行带检测在 ID 列区域 `(160,240,200,440)` 上切出（`min_px=2`），
**不要写死行 y 数组**（§6.6）。
**★行数不是固定的★**：同一局面实测一次读到 **12 行**、另一次只读到 **3 行**（列表可滚动 / 被过滤）
⇒ 不得假设「永远 12 行 / 固定 y」，每次都按行带动态切分并以**行首编号**校验。

**目的地文本的四种形态**

| 形态 | 实例 | 处理 |
|---|---|---|
| 逗号分隔 | `moveto 100,150` | 最常见 |
| 空格分隔 | `moveto 104 146` | 同一语义 |
| 近距 | `nearto 101,140` | 同一语义 |
| 无坐标 | `Brisbane, moveto` / `at sea` | 按基地名解析或判为在航，**不硬凑坐标** |

**解析纪律（按序）**
1. **按行带逐行裁剪**（整块 psm6 会把编号读错）：ID 条裁 `(166, yc-7, 182, yc+7)`、
   目的地条裁 `(712, yc-7, 1000, yc+7)`。
   **★OCR 倍率必须逐字段标定★**：编号列 = **LANCZOS 放大 6x + yc±7 → 实测 12/12 全对**
   （8x 会把 `6` 糊成 `5`，实测 TF16→TF15；4x 吐 `423`/`414` 垃圾；yc±6 会切掉首行字形顶部，`13`→`4`）；
   目的地列走 ~6x + **二值化 + 数字白名单**（见下）。
   **同一张图两个字段用不同倍率是正常的，不要「统一」。**
   **★数值列必须二值化并加数字白名单，否则字符被读成字母★**：
   实测同一张图，直接灰度 + 通用 `--psm 6/11` 把 `98 137` 读成 `movreto GR 137` / `S8 137`；
   换成「灰度 → 阈值二值化（`point(v<140?0:255)`）→ LANCZOS 放大 → `tesseract --psm 7
   -c tessedit_char_whitelist="0123456789, "`」后稳定读出 `98 137`。
   ⇒ 凡「纯数值条」（方位 / 比例 / 编号），**白名单是必需项而不是调优**——
   它一次消掉「字母被当数字、数字被当字母」这整类误读。
   ⚠ **白名单只能用在纯数值条上**：关键词与数值同条时必须先按第 2 步剥掉关键词，
   否则白名单会把 `moveto` 一并过滤成数字，连匹配都做不了。
2. **先剥关键词，再做字形归一化**。关键词用**自身容忍混淆**的正则
   `m[o0]v[e3]t[o0]|n[e3][a4]rt[o0]`；归一化只作用于关键词**之后**的片段
   （`i/l→1`、`o→0`、`S→5`、`B→8`、`g→9`）。
3. **数值区取两段数字**；若分隔符被 OCR 吃掉（`104146`），按 3+3 / 3+2 / 2+3 切分依次尝试。
4. **地图范围校验**：**不得写死珊瑚海坐标框**——改由 `bases.json` 全部有效基地格（滤掉 65535）
   的包围盒 + 外扩 8 格自解（实测推出 `x=83..129, y=108..168`），换剧本自动适配。超界判误读。
   **自检口径**：grep 数字区间常量（`<= 132`、`110 <=`）即可发现漏网的绑剧本硬编码。
5. **行归属用行首编号做实体校验**，**不许行序推断**（§6.6 泛化规则）。

> **★清洗步骤毁掉匹配步骤（本配方最容易犯的错）★**
> 把 `o→0` 之类的归一化用在**整串**上，会把关键词 `moveto` 变成 `m0vet0`，匹配正则随即恒不命中。
> ⇒ **归一化只作用于「被匹配的数值字段」，不作用于「用于匹配的关键词」。**
> ⇒ 单测必须测**完整串**（关键词 + 坐标）；只测坐标字段会漏掉这类自毁。
> 泛化：任何「先清洗、后匹配」的管道都要问一句——**「清洗会不会改掉匹配所依赖的那部分？」**

**集成读数与单体验证不一致时，先查 plumbing 再查逻辑**
症状：同一段解析逻辑**独立跑正常**（行带 12 条、解析全对），折进主工具后**读到 0 行**。
顺序：① 先核对截图辅助函数在**该调用路径**上是否真的产出了临时文件（返回值 + 文件存在性 + mtime）；
② 再怀疑行带检测；③ **最后才怀疑解析逻辑**。
把「集成读数异常」直接当成「逻辑错」去改算法，等于把已经验证正确的逻辑改坏。

### 6.8 「点击像素 ↔ 落格」无稳定映射（长距离目的地的真正拦路虎）

**实测**（同一流程内）：

| 点击像素 | 落格 | 隐含比例 |
|---|---|---|
| (500,500) | **(99,155)** | — |
| (542,300) | **(10,113)** | Δy 仅 200 px → 跳 **42 格**（≈4.8 px/格）|
| 另一处测量 | — | 240 px = **6 格**（≈40 px/格）|

**两者相差近 10 倍，不可能共存** ⇒ 两条都有可能是错的来源：
① **基准未重置**（每个样本拿上一个样本的落点当原点——实测得到的是「两轴相差过远」这类自相矛盾的斜率，
见 `perception-channels.md` §一「标定必须在每个样本之间重置基准」）；
② **地图视野确实会在两次点击之间自行移动**（游戏自身行为，非我方动作所致）。
⇒ **先按 ① 重做标定**（每样本重置基准），只有重做完仍不一致，才归因到 ②。

**★重做标定必须换读数源：用「编队列表的目的地列」而不是顶栏 `Hex`★**
上表的矛盾数据**全部**来自已作废的顶栏读数。改用**被点实体的目的地字段**（`moveto X,Y`，见 §6.7）当读数源后，
标定立刻自洽：`(512,420) → moveto 109,147`、`(512,220) → moveto 109,142` ⇒ `200 px = 5 格`，
**恰好 40.00 px/格**，与另一轴独立测得的量级一致。
⇒ 规律：**标定的读数源，必须就是「这次动作要改写的那个字段」。**
顶栏 `Hex` 是固定字段（`perception-channels.md` §一），量的是光标；
目的地方位量的是**这次点击落到了哪一格**——只有后者是闭环要的反馈。读错字段，标定必然发散。
⚠ **两点同 x 时标不出 x 刻度**：上例两次采样都在 x=512，故 x 比例仍是假定值；
x 的残余偏差只能靠**落点自证迭代**修掉（实测一次修正即精确命中）。
⇒ **不得把「x 未标定」当成失败**——闭环本来就设计成容忍它。

**后果**：
- **「标定一次就永久有效」不成立**：视野会变，任何单次标定值都可能过期；
  **每轮重测**才是常态。但**「标定 + 一次修正」已实测可命中**——
  用目的地列作读数源、两点标定后算目标像素，误差一次修正即到 0（实取格 = 目标格）。
- 可用的闭环：**读目的地列 → 两点标定 → 算像素落子 → 回读修正（1~2 轮）**。
  → **近距目标**（当前视野内）已实测可收敛到精确命中。
- **远距（视野外）目标：先走「列表导航」把视图开过去**（`perception-channels.md` §一：
  点基地 / 单位列表里的基地名即跳转，全屏差 ~33%）；**列表里找不到该实体**才判 `failed`，
  **不得粉饰成功**。这条能力缺口要显式上报，不要用「偶尔点不准」的描述把它掩盖成偶发故障。
  ⇒ ⚠ **「列表导航」只解决「视图开过去」；「落到指定格」仍需现场两点标定 + 落点自证**——
  两者是两步，完成前者不等于完成后者。

### 6.9 小地图：**不是**定位手段（实测否证）

- **布局**：小地图区域约 `(892,664)–(1020,764)`；视野红框约 `(962–988, 704–729)`。
- **实测结果**：点小地图（含红框内外多个点）**不影响视图** ——
  全屏逐字节差 **0.00%**（旧记录称「点红框之外视野会跳转」与「点红框内只是居中」，**均不成立**）。
- ⇒ **不要再把小地图当定位手段**，也不要去标定它。
  需要绝对定位时，走**基地/单位列表**（点基地名即跳转，见 §6.3 / `perception-channels.md` §一）。
- ⚠ **工具自身的「小地图重定位」兜底路径也是死的**：落子工具在目标像素超出可点区时会尝试小地图重定位，
  实测抛 `'NoneType' object is not subscriptable` 后回落成「只好钳位」——
  即**该兜底一旦触发，产出的必然是错误落点**（且只会打印一行告警，不影响退出码）。
  ⇒ 见到这条告警**不要当成偶发**：按 §6.3 先自己把视野移到目标附近，再落子；
  更不要靠多轮重试等它自愈（它会一直钳到同一格）。

### 6.10 在线估计的参量被单次误读毒化 → 闭环原地踏步

- **症状**：纠偏闭环不再收敛——**多轮点击落在同一像素**、偏差纹丝不动。
  外表极像「控件失效」或「比例错了」，于是排障被引向错误方向。
- **机制**：闭环用「上一轮的（点击像素, 实际落格）」反推 px/格 比例。**只要有一轮读数错**，
  反推出的比例就是荒谬值（实测算出 `0.16` / `-2.00` px/格）——此后每轮的修正量 ≈ 0，
  于是**原地空转到跑满轮次**。而每一轮都会照常打印「第 N 轮：点击像素…」，日志毫无异常。
- **处置**：
  1. **任何在线估计的参量都要有范围闸门**（量纲 + 合理区间，如 px/格 只接受 5~60），
     越界即**丢弃该轮估计、沿用上次好值 / 或回落默认值**——宁可保守，不可被一次误读带飞。
     ⚠ **不要以为“坏估计只会让闭环停滞”——它会主动把对象推向目标的反方向**：
     实测 OCR 把 `100` 读成 `17` 之类，两点标定算出 **9.52 px/格**（真值 40.0），
     用它算落点于是把「向后撤离」的编队设到了**更靠近敌区**的格（目标 y=144，实得 y=132）。
     所以坏估计的后果不是「不收敛」，而是**看似成功的反向移动**——比停滞危险得多。
     闸门区间不要凭空定：**先用干净样本实测出真值，再按真值 ±50% 定闸**，
     过窄会把合法值也丢掉、过宽拦不住毒化。
  2. **加停滞检测**：连续 N 轮点击像素或落点不变 ⇒ 立即判 `failed` 上报，不要跑满轮次。
- **泛化**：闭环里「由单次观测反推出来的参数」（比例、偏移、基准）都是**放大器**——
  观测噪声被它放大成系统性错误。**估计值必须先过合理性闸门，再进入控制律。**

### 6.11 成功判据用了代理指标 → 把「做反了」报成成功

- **症状**：脚本打印 `✅ 成功`，但被操作的对象实际上停在了**目标的反方向**（或根本未达目标）。
  比静默失败更糟：失败会被上游看见，**假成功会被当成已完成写入下一步推理**。
- **机制**：成功判据写成了**当时目标的一个代理指标**，而该指标与该次动作的真实目标**方向相反**。
  实测：把“编队进胜负点打击半径”阶段的判据 `距胜负点 ≤ 7 格` 留在了同一个脚本里，
  后来用它做“**向后撤离**”——于是脚本把「撤到距胜负点 2 格」判定为 `✅ 成功`。
- **处置**：
  1. **判据永远直接比对「本次动作的目标本身」**，带显式容差，并分别报出 x/y 差值：
     `abs(实得 − 目标) <= 容差`。**容差不得用「距某固定点的距离」这种代理量代替。**
  2. 用同一份脚本干**方向相反**的两件事（进 / 退）时，**必须重新检视判据**，
     因为任何一个“离目标点多近”的指标都天然只对其中一个方向成立。
  3. 失败分支要打印**实得值与差值**（`实得 (x,y)，x差 +n / y差 -m`），让“差多少”可见；
     只报「未命中」的话，上游无法判断该重试还是该换目标。
- **泛化**：凡脚本带「目标」语义（目的地 / 百分比 / 数量），成功判据只允许是**目标本身**。
  写下任何 `<= N` / `>= N` / `接近` 式的判据前，先问：**「这个指标会不会在某个方向上把反向结果也放行？」**

### 6.12 `import -crop` 的 PNG 带页面偏移 → 后续 `convert -crop` 全部错位

- **症状**：按计算好的坐标裁剪某个界面区域，裁出来的内容**整体错位固定量**（实测偏下偏右）；
  同一段裁剪逻辑在另一个脚本里却正常——于是很容易误判成「列表行 y 猜错了」「面板布局变了」。
- **机制**：`import -window root -crop WxH+ox+oy out.png` 产出的 PNG **带页面几何**
  （如 `1400x1050+188+150`）。之后 `convert out.png -crop WxH+x+y` 是**按页面坐标**解释的，
  偏移被叠加一次。实测表现：顶栏确实在图像 `y=2..24`，却要裁到 `y≈140` 才看得见
  （恰好是窗口偏移 150 的量级）。
  ⇒ **这不是「行 y 算错了」，是坐标系整体平移了**；而它**不报错**，只给出错误内容，
  极易被当成 OCR 质量差或布局变化，把排障引向错误方向。
- **处置（任选其一，不要「两者混用后凭感觉判」）**：
  1. 截图时加 `+repage` 让 PNG 变成 `WxH+0+0`，后续 `convert -crop` 即按图像坐标；
  2. **改用 PIL 裁剪**（`Image.open(p).crop((x0,y0,x1,y1))`）——PIL 一律按图像坐标，最省心。
  ⚠ 截图辅助函数产出的图**不一定**带偏移（取决于调用方式），所以**同一脚本内两种图混用**是常态；
  一旦混用，就必须逐个确认坐标系，不能推定它们是同一套。
- **通用形式**：**图像裁剪前先问一句「这张图的原点在哪」**。
  凡是「坐标算得很确定、内容却偏一个固定量」的裁剪/点击问题，先查**坐标系是否被叠加/未归一**，
  再查「坐标本身算错」。
- **★配套：放大量纲必须在「生成」与「反算」两侧一致★**
  把放大系数变量在生成侧当作**倍数**用（`resize(w*sc)`），在反算侧却当作**百分比**用
  （`val*100/sc`），会让所有换算后的坐标**整体放大 100 倍**，产出 `y=2327` 这类根本不存在的行号。
  ⇒ 症状与 §6.12 同类（都对不上、都不报错），但根因是**量纲不一致**而非坐标系叠加。
  ⇒ 写法：变量名带单位（`pct=500` / `mult=5`），或两侧统一只用一个常量。**换算出的坐标必须过合理性闸门**
  （行号须落在截图高度内），一眼就能拦住这类错。

### 6.13 换阵营 / 换剧本时的「写死单侧」缺陷扫描（换侧首次推演的必做项）

**换阵营是检验抽象是否真的一般的最好实验**：一条在 A 侧跑了多局的流水线，搬到镜像的 B 侧时，
凡是**写死 A 侧字面量 / 布局常量**的地方会**同时失效**，而症状是「静默失败」而不是报错。

- **必扫五类（换侧第一件事，用 grep，不靠回忆）**：

  | 类别 | 形态 | 失效后果 |
  |---|---|---|
  | 读层侧参数 | scraper / 读取器写死 `--allied` | **该侧 0 舰可读**，感知层彻底失明 |
  | 阵营字面量判据 | `== 'ALLIED'` / `== "USNAVY"` / 部队名前缀 | 判据恒为假，动作链“找不到目标”而中止 |
  | 列表布局常量 | 列 x 阈值 / 裁窗偏移 / 行距 | 行/列全部扫不到，**返回空列表** |
  | 编制名前缀 | 如战斗中队只认字母前缀 | 该侧同类中队全被判错类别，去错列表里找 |
  | 界面入口 | 只认某种界面状态（如只认某个顶栏词） | 面板开着时顶栏被遮 → 误判「不在可操作状态」 |
  | **面板/控件区常量** | 面板 y 范围、按钮相对偏移按**另一个列表**标定 | 面板明明开着却判「未打开」→ 动作中止；或按钮点到了别的控件 |

  ⇒ 面板/控件区常量这一类**特别隐蔽**：同一个「航空队详情面板」，**舰载中队列表（N）与陆基中队列表（A）**
  的布局**不在同一位置**。实测从 N 列表标定的面板常量 `y=300..465`，套到 A 列表时
  搜索控制区实际在 **y≈160–210** ⇒ 面板判定恒为否（「未能打开详情面板」）。
  同类：按钮相对偏移从 N 列表标定 `+90/+111`，A 列表实测是 `697/743`。
  同类：**数值栏的显示格式也不同** —— A 列表的搜索 / 比例栏是「`当前/总量`」形态（实测 `81/3230`），
  N 列表是纯百分数。只按纯数字解析的读回函数在 A 列表**恒返回 `None`**，
  症状是「命令像是没生效」的**假失败**——而它其实已经生效，只有结算后读层的 `percent_search` 才证实。
  ⇒ 面板读数一律以**结算后读层字段**为核验口径，界面读数只作辅助（配 SKILL.md §5.8）。
  ⇒ **修法：改「自适应范围扫描」而不是再写死另一组常量**。
  面板判定 = 先在**足够宽的 y 区间**内扫描特征词（`Naval Search`/`ASW`/`Patrol`/`Supply`），
  命中即认为面板已开；按钮位置 = **按像素簇自适应取前四个簇的中心**，
  不去假设「首簇 + 固定偏移」。同理：行号一律动态切带，不写死行 y 数组。
  ⇒ 通用形式：**凡「先在一处标定、再用到另一处」的屏幕常量，都是写死单侧的变体**；
  换侧/换列表时把它们换成「在宽区间里自己找」。

  ⇒ 扫法：`grep -rnE "'ALLIED'|'USNAVY'|'IJN'|VP-|VF-|VB-" <工具目录>`（同时扫工具本体与脚本库）。
  ⇒ **同一类缺陷会在多个命令里各写一遍 —— 发现一处后必须对整个命令面全扫，不能只修遇到的那一个**。
  已实测受影响：`set-cap`（后缀唯一性判据）、`set-mission`（写死只开 N 列表 + 逐词精确比对）、
  `set-search`（写死盟军中队前缀，兼有上面的面板常量 / 按钮偏移两处）、
  `strike-audit`（写死 `nation == "USNAVY"`）、编队列表编号列（x 阈值写死盟军布局）。
- **根治写法：判据改从**读层权威数据**推导，而不是从字面量**。
  典型做法：不写“哪种名字算舰载机”，而是**查读层里航母记录的 airgroups 子名单**；
  不写“哪个国籍算我方”，而是取**读层里出现次数最多的国籍**。两者都是零硬编码且天然阵营无关。
- **侧参数必须可配且显式**：改由一个小配置文件（如 `side.txt`）驱动，并**在输出里打印当前侧**
  （`读层阵营：JAPAN（来自 …/side.txt）`），否则「读到了另一侧」没有任何提示。
- **★静默失败的代码病根：中止时用 `return` 而不是 `exit(1)`★**
  工具内部函数 `return` 只结束本函数，**进程退出码仍为 0**，调用方 / 脚本 / 日志全部看起来正常。
  实测症状是「命令成功但游戏没变」。⇒ **凡“未完成预期动作就放弃”的分支，一律以非零退出码结束**，
  并在汇总层把失败条目显式标成 `FAILED`（不得无条件记 `done`）。
- **★批量命令不得无条件报成功★**：`set-X-all` 类命令逐项调子命令时，
  子命令内部“定位失败→return”会被外层当成功——实测 4 个目标里 2 个根本没设，汇总却报 4/4 `done`。
  修法：**捕获子命令输出并检索失败标志词**，逐项定成败；有失败则显式报「N/M 未成功」。
- **★别拿“换侧后测试”当唯一手段★**：这类缺陷的正确防法是在写时就避免字面量；
  换侧只是 **事后检验**。但**换侧后必须显式跑一遍“枚举全部实体”的命令**（如列出全部编队 / 全部航空队），
  确认数量与预期同量级——实测这一步直接揭出了“0 舰可读”与“列列全空”两个地基级故障。
- **★量化控件的步进逻辑不得假设当前值是步长的整数倍★**
  面板上的百分比 / 挡位控件通常是「归零键 + 递增键 + 直接置满键」。若步进次数写成
  `(目标 − 当前) / 步长`，当**当前值不是步长整数倍**时结果就落不到目标上
  （实测：当前 15、目标 60、步长 10 → 步进 4 次得 **55**，差 5）。
  ⇒ 正解：**先按归零键，再从 0 逐次递增到目标**——结果与当前值无关。
  ⇒ 配合同层判据必须**精确相等**（见 SKILL.md §5.8）：本例旧判据带 ±10 容差，
  把 55 报成了 `✓ 成功`。**两个缺陷叠在一起就会自洽地输出错值**——修一个不够，两个都要修。

### 6.14 列表行定位：用**解析式**而不是 OCR 搜索

- **原理**：游戏列表按实体编号**升序**排列，行距是 UI 常量。
  ⇒ `行 y = 基准 y + 行距 × (该实体在升序编号表中的下标)` **可解算得出**，
  **不需要 OCR 搜索行**。下标表从读层取（如 `taskforces.json` 的 `record_id` 排序）。
- **为何必须这样做**：OCR 会**丢中队列名的前缀**（如把 `EI-1` 读成 `ELE`、`EII-1` 读成 `14`），
  使 `EI-1` 与 `EII-1` **在文本上不可区分**。靠名称匹配的定位**本质上做不对**，
  与“OCR 调优”无关——丢了前缀就没有鉴别信息了。
- **正确方式 = “以公式定行，以 OCR 仅作核验”**：
  1. 先**滚到列表顶部**（列表可能停在任意滚动位置；不滚到顶会只看到一段）；
  2. 从读层取升序编号表，算出目标行 y；
  3. OCR 只用于**一致性校验**：统计“扫描到的行 y”与“公式行 y”的吻合数，
     达到多数（实测 60% 阈值即可）即**以公式为准**——单行 OCR 误读不会带偏定位。
  ⇒ 反向选择（以 OCR 读数为准）会把“行 5 的 5 误读成 7”变成“把第 7 号定位到第 5 号的行”，实测踩过。
- **配套：提供 `--row <y>` 强制指定行**作为诊断通道（绕过自动定位）。
  发现命令行参数**已被 argparse 定义但代码里从未使用**时，它就是个假接口，修时要一并接上。
- **行 y 与“窗口偏移”无关**：工具的截图函数产出的图起点即游戏坐标；
  而自己手写的 `import -crop` 图带页面偏移（见 §6.12）。**两者混用时先对齐坐标系再比行 y。**

### 6.15 边缘悬停滚动：**有效**，但触发带只有 1 px 宽（旧否证已作废）

**规则：把鼠标停到窗口的绝对最外 1 像素** —— 左 `x=0` / 右 `x=W−1` / 下 `y=H−1`（窗口内坐标），
视野即朝该方向平移。手册 4.2.5 原文印证：*“…or **scroll the mouse cursor to the Tactical Map's edges**
in order to move the map view.”*

**实测数据（命中与未命中的唯一变量 = 离边几个像素）**：

| 该侧位置（窗口内） | 画面变化 | 判定 |
|---|---|---|
| 左 `x=0` | 22.5% | ★滚动（视野**西移**）|
| 左 `x=3` | 0.0% | 无效 |
| 右 `x=W−1` | 22.5% | ★滚动（视野**东移**）|
| 右 `x=W−2` | 0.0% | 无效 |
| 下 `y=H−1` | 24.1% | ★滚动（视野**南移**）|
| 下 `y=H−2` | 0.0% | 无效 |
| 上 `y=0` | 0.0% | 无效（被窗口标题栏占用）|

⇒ **差 1 px 就完全失效，且失效的样子与「该通道不存在」一模一样** ——
这正是本文件长期把「停边缘」写成已定论否定的原因；那份否定还“改走生产入口复测”过一遍，
让它看起来格外可信。**它错在测的是窗口内侧点位，不是边界本身。**

**★它不能单独当导航用（能力边界）★**
- **只有位移，没有绝对定位**：滚多少格取决于**悬停时长**，速率不可精确控制；
  且地图内容重复时互相关会**误匹配**（实测同一方向两次得到相同位移，实为匹配到同一张图）。
- ⇒ 用法 = **给「列表点名」做最后的细位移**，或把超出可点区的目标推进视野（配 §6.3）。
  **绝不可拿「滚了几次」当落点证据**；落点/视野仍须回读核验（列表读数或结算后读层）。

**★测位移的装置纪律（否则会把真实滚动测成零位移）★**
- **不要在两个样本之间把视野 park 回原位** —— 那样互相关每次都匹配到同一张图，
  读出「各次位移完全相同」的假象，把真实的滚动掩盖掉（实测踩过，一度以为装置坏了）。
- 每样本独立量：悬停前取一帧 → 悬停 N 秒 → 取一帧 → 逐字节差判「动没动」，
  再用互相关求位移方向与量级。
- ⇒ 与 §6.15 同源的通则：**凡是「边界型控件」（屏幕边缘、列表最末行、面板相接处），
  必须测到边界本身的像素**；内侧附近测出的否定结论不可信。

## 7. 进程与环境判定的假信号（「游戏是不是关了 / 是不是我点坏了」）

判断游戏是否还活着，有三种**看起来像证据、其实不是**的信号：

| 假信号 | 真相 | 正确做法 |
|---|---|---|
| `pgrep -f <关键词>` 报有进程 | **匹配到的是它自己的命令行**（`pgrep` 的 pattern 出现在自己的 `args` 里）| 用 `ps -eo pid,etime,rss,args \| grep -F "<完整 exe 名>" \| grep -v grep` |
| `ps -eo comm` 里找不到游戏 | `comm` **只保留前 15 字符**，长 exe 名被截断，永远匹配不上 | 改用 `args` 列，不要用 `comm` |
| 屏幕全黑 / 窗口偏移读成 `(0,0)` | 可能是窗口真的没了，也可能只是**偏移探测失败**（两者症状相同）| **三层分开验**：① 进程 ② 窗口树（按 1020~1032×764~792 匹配 + 边框内缩）③ X 根画面均值 |

**存档写在回合边界**：游戏在**命令阶段**崩掉时，**上一回合结算后的 autosave 完好**，
内存里的当回合命令随进程消失。⇒ 崩溃后的正确顺序是**先核存档（mtime + 读层日期）确认进度**，
再 `recover` 重启载入；**不要**在没核存档的情况下断言「进度丢了」，也不要因为一次崩溃就改写战术结论。

**★由此推出的执行纪律：改完一组就立刻结算落档，不要「攒着一起做」★**

- **规则**：凡在多回合里分次下达的改动，**每完成一组自洽的改动（例如「本回合该改的编队全部改完」）
  就立即过一次回合把它落进存档**；不要跨越多轮交互累积内存态指令。
- **理由**：进程退出是**随时可能**的，而**只有结算才把命令写进 `.pws`**。
  攒着做的代价是：中途一次退出会**静默丢弃自上次结算以来的全部改动**，而日志上没有任何迹象——
  你看到的仍是「已经改好了」的回执。实测：三支编队计划依次改派，第一支改完后进程退出，
  该改动**未落档**，重启载入后回到原值，前一轮的工作全部作废。
- **自检**：每轮结束时间一句「我这几轮下的令，有多少已经进过结算？」
  凡是**未经过结算**的改动，一律视为「尚未生效」，不得在汇报里当成已完成。
- 与 `evidence-and-archive.md` 的三层证据链一致：**指令层回读不是真值**，结算后的读层才是——
  「没结算」等价于「还没有值」。
